# Software Development

Turns a repository's issues into verified pull requests, and keeps an owner's software portfolio in view. The software factory is the issue loop: `software-developer` works one repository from its GitHub issues, triaging and planning itself, having workers build and fix in their own worktrees, with GitHub holding the state, and merges verified agent work into the integration branch only; promotion to production stays with people. Around it sit a release preparer, a weekly portfolio review, an issue harvest that turns what people say about the software into well-formed issues, and the owner-started methods for specs, schema documentation and doc cleanup. This department also holds the two skills every orchestrator in the toolbox uses: `orchestration-workstream` (how any worker behaves and returns) and `orchestrator-scaffold` (how to build a new orchestrator, and the template every agent file follows).

## The plugin

This folder is a standalone Claude Code plugin named `software` (`.claude-plugin/plugin.json`). Its `agents/`, `skills/` and `bin/` are the plugin's, and it depends on no other department.

- **Agents** are lightweight: one main agent per job, saying the goal, the inputs, what done is, what it must never do, its tools and the skills it loads. Two department agents do dispatched work: `software-worker` (a slice in parallel or in its own context) and `software-reviewer` (independent judgment).
- **Skills** hold the know-how: each job's skill carries the procedure, the checklists and formats, and the `##` sections a worker or the reviewer is told to follow. A main session does not get its `skills:` preloaded, so each main agent's first instruction is to load them with the Skill tool.
- **Commands** are in `bin/`: one wrapper per script, generated by `python3 scripts/build_bins.py software` from the toolbox root. The plugin puts `bin/` on PATH, so a skill says `software-repo-status OWNER/REPO` and an agent grants `Bash(software-repo-status:*)`. `python3 scripts/toolbox_check.py` fails when a script has no wrapper or a wrapper has no script.

Under the plugin, agents and skills carry the plugin's name as a prefix: `software:software-developer`, `software:software-issue-loop`. Both `--agent software:software-developer` and `--agent software-developer` start the main agent; an `Agent` dispatch names `software-worker` or `software-reviewer`.

### Using it interactively

```bash
claude --plugin-dir ~/coding-projects/automation-toolbox/software                 # this session only
claude --plugin-dir ~/coding-projects/automation-toolbox/software --agent software:software-developer
```

Or enable it for one project, so sessions in a software repository see the software skills and agents and sessions elsewhere do not: install it from a marketplace that lists this folder, and set `"enabledPlugins": {"software@<marketplace>": true}` in that project's `.claude/settings.json`.

### Using it from Sentinel

An Automation launches a main agent by name with `--plugin-dir <toolbox>/software`, which also puts the commands on PATH for the session. Allow the `Skill` and `Agent` tools, and the command rules as the agent's `tools:` line writes them (`Bash(software-repo-status:*)`). A prepare or finish step runs a command from `<toolbox>/software/bin/` (for example `software-issue-harvest-sync`, `software-issue-file`), or the same script by path. The overlay's `subagents:` lists `software-worker` and `software-reviewer`.

### The merge guard

`software-developer` merges agent PRs only through `software-pr-merge`, which reads the PR and the repository from GitHub and refuses a merge into the default branch or any of main, master, prod and production, a PR without the `ai-agent` label, a draft, and a PR whose checks are failing or pending. It exists because nothing else stops such a merge: branch protection (F3-BRANCH-4) is not available for private repositories on every GitHub plan, and a permission rule sees the command, not the PR's base. The agent file allows `software-pr-merge` and only the `gh pr` subcommands the loop needs (`view`, `diff`, `checks`, `list`, `create`, `edit`, `comment`, `ready`), so `gh pr merge` is not allowed by it. A runner that grants the session bare `Bash` (a Sentinel overlay's `extra_tools`) must also deny `Bash(gh pr merge:*)`, since a bare `Bash` grant would otherwise allow it again; the workers' calls are checked against the same list.

### Settings and environment

The keys are described in [docs/settings.md](../docs/settings.md).

- **Issue loop**: `gh`, signed in, and a local clone of the repository; the brief names where the design rules are. It reads no settings file. The integration branch is `development` unless the brief names another (`software-pr-merge --integration`).
- **Issue harvest**: `repos_file` under `[issue-harvest-workstream]` (the repo map) is required; `state`, `horizon_days`, `closed_days`, `public_denylist_files`, `private_terms` and the `sources` sub-tables are optional. It reads the Portal through `portal_mcp_config`, with the bearer in `INSIGHTS_PORTAL_ASSISTANT_TOKEN` or a `${VAR}` in the MCP config.
- **Portfolio review**: `repos_root` under `[software-portfolio-review]`, or a folder argument to `software-repo-sweep`.
- **Scaffold lint**: `F3I_TOOLBOX_DENYLIST` (files of private names, `:`-separated).
- Python 3.11 or later, with `pyyaml`, declared in each script's `# /// script` block; `bash` for the `.sh` commands.

## Bringing up the issue loop

The issue loop is the toolbox's software factory. It replaced an earlier offline factory, retired on 2026-10-11 and kept in git history. It is brought up in three steps. Each step starts only when the one before it works, because the corrections found in an earlier step are the only instructions worth adding.

1. **You are the orchestrator.** In an ordinary Claude Code session in the repository's clone, with the plugin on, ask for one job at a time (the prompts below) and watch. Write down only what it gets wrong; those corrections go into the skill's sections. No Sentinel, no orchestrator.
2. **The orchestrator chooses, interactively.** When triage, plan and build each work by hand, run `software-developer` in an interactive session and watch what it picks and delegates. The new question is only whether it chooses well.
3. **Sentinel runs it unattended.** Only once watching is boring.

Principles behind it:

- Prove the job by hand before automating it; automate what you find yourself repeating.
- Prompts state goals and principles, not procedures. Add a rule only for a mistake the agent actually made.
- Rules live once, in the design rules (`F3-AGENT`, `F3-BRANCH`, `F3-DOC`); prompts point at them.
- Configuration (schedules, tools, caps) lives in the runner, not in the prompts.

A candidate to bring in later: the retired factory's script-run verification (the repo's declared checks run from the base commit in a clean worktree, and a repro that fails before the fix and passes after it). Its script is in git history.

### Step 1 prompts

Run in Claude Code from the repository's clone. Replace the issue numbers.

**Triage**
> Read this repo's own docs (agent file, README, vision, handoff) and the F3-AGENT rules in the design rules. Then triage issues #16 to #20: for each, decide whether it is ready to build, needs a plan first, needs a question answered, or is blocked; set a type and status label; and leave one short comment saying what it needs next. Create any missing labels.

**Plan**
> Read this repo's docs and the F3-AGENT rules. Write the plan for issue #N as docs/plans/N-slug.md, one page of decisions and risks (goal, approach, decisions, out of scope, verification, size) on branch issue/N-slug, open it as a draft PR labeled ai-agent, and comment on the issue. Then stop for my review.

**Build**
> Read this repo's docs and the F3-AGENT rules. Build issue #N (following docs/plans/N-slug.md if it exists): a failing test first for a bug, the repo's own checks before you finish, and the PR into the integration branch labeled ai-agent, saying how it was verified. Do not merge.

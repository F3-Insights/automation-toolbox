# When no one is present

Read by `SKILL.md`, and by `reporting-weekly-report` every session.

Unattended, this procedure is run by `reporting-weekly-report`, in two scheduled sessions a week: a collection run on Thursday and an assembly run on Friday. The gates are still asked, every week; they are asked on the owner's task list rather than in the terminal, and nobody waits for the answer.

- **Collection in code.** `report-weekly-prepare` runs Stages 1 to 5 before the session and writes the week into `<store>/work/<period>/`, one folder per week, so the second session and the owner's answers find the same files the first one left.
- **Gates 1 and 2 are one numbered list.** `reporting-report-weekly-gates build` numbers every question the two gates ask (the categories, the proposals, the misfiled and left-out items, the carry-overs, the workers' questions, the wins, the silences, the missing figures, the table) and states a default beside each. One `comms-confirm` request puts it on the owner's list with the fallback `proceed`, and one message tells them it is there.
- **The answers, or the defaults.** At assembly, `reporting-report-weekly-gates apply` turns the owner's reply into `gate1.json` and `owner-input.md`. A number nobody answered takes its stated default: the standing categories as the profile has them, nothing moved, pulled back or struck, no wins added, a missing figure "not available this week", and a question's item held out as pending. `owner-input.md` and the covering note name every default taken.
- **Gate 3 is the owner's approval, and it is never assumed.** The draft is rendered as `weekly-<period>-DRAFT` and a second request, fallback `wait`, asks the owner to approve it. Nothing is recorded to the ledger until they do.
- `report-weekly-check` computes where the week stands from those files, and its `--precheck` is what the schedules start on.
- Never create an email draft and never write a file outside the store and the report folder the run names. No delivery is made.
- Never record a report to the ledger that the executive has not approved.
- A profile that is missing, fails `reporting-report-profile validate` or is due for review stops the week: the setup interview needs the owner present.

## Done is computed

`reporting-report-weekly-check STORE --period PERIOD --phase PHASE --report-folder FOLDER --format json` computes seven tests from the week's files: evidence, gates, sections, numbers, continuity, rendered, recorded. Its `next` names the next step and who it waits on, and `earlier` lists earlier weeks the owner approved that are not yet kept. Run it first and last in every session and after each step; report its result, never your own view of it.

- The **collect** phase is done when the evidence is judged and the gate questions are out.
- The **assemble** phase is done when the draft is verified, rendered and put to the owner.
- The week is done when the owner approved it and `report-record` kept it.

## The week folder

`STORE/work/<period>/` holds `prepare.json`, `ledger.json`, `pack.json`, `digest.md`, `facts.json`, `continuity.txt`, `editor.txt`, `verdicts.json`, `questions.json`, `gates.json`, `gates.md`, `CONFIRMATIONS.md`, `gate-answers.json`, `gate1.json`, `owner-input.md`, `draft.md`, `approval.md`, `approved.md` and `LOG.md`. Write only those names, and only by absolute path. Save each worker's output to its file with `Write` as soon as it returns; workers never write the week's files.

## The session, step by step

These add to `SKILL.md`'s Steps what only the unattended run needs.

1. **Orient.** Read `SKILL.md`, this file, the profile and the week folder; run the check. On `profile` (no profile, one that does not validate, or a review that is due), stop: the owner runs the setup interview with someone present. Say so in one line; it is the only thing that blocks the week outright. Launched by hand with no prepare step, run `reporting-report-weekly-prepare STORE --scope SCOPE --period PERIOD --phase PHASE` first.
2. **Answers first.** `confirm check STORE/work` records what the owner answered on any week's task. Keep every week in the check's `earlier` list before this week's work.
3. **Collect** (`next` is `collect`): the prepare step failed or did not run. Read why; run it once. For the harvester tier, dispatch `reporting-worker` on `workers/harvester.md` to write `ledger.json`, run `reporting-report-collect --validate`, then organise as Stage 5 does.
4. **Judge** (`judge`). Where a direct report's update arrived as one long piece of prose, run `reporting-worker` on `workers/intake.md` first. Dispatch the continuity worker (only when `candidates.json` lists any) and the audience editor in parallel, save `continuity.txt` and `editor.txt`, then `reporting-report-questions verdicts --from EDITOR --out verdicts.json` and `reporting-report-questions collect` over both outputs into `questions.json`.
5. **Ask the gates** (`ask-gates`). `reporting-report-weekly-gates build WEEK --due DUE` (DUE is the day before the period, or today if later) numbers every Gate 1 and Gate 2 question with its default into `gates.md`. Put it on the owner's list with one `comms-confirm` request: `confirm new STORE/work/PERIOD/CONFIRMATIONS.md --question "Weekly report gates for the week ending PERIOD: answer the numbered list in gates.md, one line per number" --of owner --channel task --due DUE --fallback proceed --assume "every default stated in gates.md" --context <gates.md path> --by reporting-weekly-report`, then its `task` and `relay`. Then `reporting-report-workorder wait --gate gate1 --questions N --no-portal`. The collect phase is done; end the session.
6. **Apply the gates** (`apply-gates`). Read the request's Answer and Evidence. Write `gate-answers.json` (its shape is in `reporting-report-weekly-gates --help`): the owner's reply verbatim, each number they answered (`yes` or `no` for a proposal, their words for a text question), and anything they asked that no number holds (a category to add by name, a rename, "make it permanent") in `gate1_extra`. Strike the carry-overs the continuity worker put under Leave out in `gate1_extra.carry_overs.strike` unless the owner kept one. No answer by the due date means `answers` is empty and every default is taken. Then `reporting-report-weekly-gates apply WEEK --answers gate-answers.json`, and close the request with `confirm close` (`--answer` and `--evidence`, or `--assumed`). A figure the owner gave goes in with `reporting-report-facts set`, a table they pasted with `reporting-report-facts add-table --from <the table saved as a file in the week folder>`; then `reporting-report-facts validate`. Edit the profile only where the owner said the change is permanent, and only the categories they named. Re-run `reporting-report-organize` with `--gate1`, `--ledger-candidates` and `--facts`.
7. **Write and verify** (`write`, `fix-draft`). Dispatch one writer exactly as Stage 12 does, with `owner-input.md` and the answered questions as the executive's answers. Save the report alone to `draft.md`. Run the check: a gap in sections, numbers or continuity goes back to the writer once, with the check's lines and the instruction to fix or cut those sentences and nothing else. Still failing after that, carry on and put the gaps in front of the owner at the approval; never invent a figure to close one.
8. **Render and ask** (`render`, `ask-approval`). `reporting-report-render --report draft.md --facts facts.json --out-dir FOLDER/PERIOD --name weekly-PERIOD-DRAFT --format all --max-pages 2 --json`; over the cap, the writer cuts detail once, never a category. Write `approval.md`: the PDF's path and page count, the covering note, each audience-bar finding and each remaining gap as a numbered line with the sentence it fired on, the items held out for unanswered questions, and the defaults the gates took. Then one `comms-confirm` request: `confirm new ... --question "Weekly report draft for the week ending PERIOD: reply ok to approve, or say what to change, per number in approval.md" --of owner --channel task --due PERIOD --fallback wait --context <the PDF> --context <approval.md> --by reporting-weekly-report`, its `task` and `relay`, and `reporting-report-workorder wait --gate gate3 --no-portal`. The assemble phase is done.
9. **Keep an approved week** (`approve`, `record`). "ok" means the draft is the approved text; changes are made exactly as the owner worded them and nothing else; "skip" means no report this week: close the work order with that note and record nothing. Write `approved.md`, run the check (the owner's approval overrules the advisory findings), render the final (`--name weekly-PERIOD`), then `reporting-report-record save` with every file Stage 17 names, read its manifest back (`ledger_pending` false), `reporting-report-record learn --last 8 --json` for proposals you report and apply none of, `reporting-report-workorder close --no-portal`, and `confirm close` on the draft request with the answer and its evidence.
10. **Close the session.** Append one entry to the week's `LOG.md` (`## yyyy-mm-dd HH:MM by reporting-weekly-report`, then `- Done:`, `- Files:`, `- Decisions:`, `- Open:`), run the check last and report its result.

## What only the owner decides

The gate list is the whole of it: what the week was about, the wins the data cannot see, the figures and tables nobody supplied, the questions a worker could not settle, and whether the draft goes. Everything else proceeds on evidence. Never ask twice: one gates request and one draft request per week, each relayed once. A worker's question goes in the gate list, never to the owner on its own. The Portal is read through the collection only; the one write is the owner's own task that `comms-confirm` creates for each request.

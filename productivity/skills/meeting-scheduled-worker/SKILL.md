# Process stored meeting transcripts

The Portal stores every Fellow recording. This skill turns the ones not yet processed into the recording's meeting note (rewritten from the transcript, with its links), the action tasks the room accepted, and the targeted enrichment hand-offs, then acknowledges the recording so the Portal stops listing it. It is the orchestrator: run it in the main session or as the `meeting-transcript-orchestrator` agent, because it dispatches two workers per recording. It never stops to ask the owner: a recording with a question for the owner is written with everything the question does not block, its admin task waits on the owner in the Portal, and a later run picks up the answer.

**One recording is one unit of work**: whatever happens to a recording (a command error, a Portal error, a failed check, a transcript over the cap) is recorded for that recording and the run moves to the next. Only two things end a run early: the Portal handing processing away from this host, and running out of recordings.

The commands, each printing one JSON object (`rules.md` has the exit codes):

```bash
python3 ~/.claude/skills/meeting-scheduled-worker/scripts/meeting_pending.py --limit 5                               # the recordings for this run, oldest first
python3 ~/.claude/skills/meeting-scheduled-worker/scripts/meeting_existing.py RID --digest D --out REC/existing.json # what the Portal already holds, the owner's answers
python3 ~/.claude/skills/meeting-scheduled-worker/scripts/meeting_fetch.py RID --digest D                            # the exact transcript into REC/
python3 ~/.claude/skills/meeting-scheduled-worker/scripts/meeting_validate.py REC                                    # plan.json against the transcript and the note
python3 ~/.claude/skills/meeting-scheduled-worker/scripts/meeting_publish.py REC                                     # the writes, then the acknowledgment
python3 ~/.claude/skills/meeting-scheduled-worker/scripts/meeting_acknowledge.py RID --digest D                      # acknowledge a recording already written
python3 ~/.claude/skills/meeting-scheduled-worker/scripts/meeting_skip.py RID --digest D --reason "..."              # record why one was skipped
```

`RID` is the recording id and `D` its transcript digest, both from the listing. `REC` is the recording's folder, `<state>/recordings/<RID>-<D>/` under the state folder in `rules.md` (`--state`, else `$MEETING_PROCESSING_STATE`, else the `state_dir` setting under `[meeting-scheduled-worker]`, else `meeting-processing/` under the top-level `state_dir` setting; with none of these the commands stop. This skill's Write permission covers `~/.local/state/meeting-processing/`, so set `state_dir = "~/.local/state"` or widen it); every command that takes the recording prints it as `folder`, and `--out` and `--answers` are refused anywhere else. `meeting-publish` reads `REC/answers.md` itself whenever it exists, so the owner's answers apply whether or not they are passed. The run folder (`RUN`) is the one the runner passes, or a new dated folder under the state folder.

`rules.md` beside this file holds the owner's settings (how many per run, the cut-off date (the `since` setting), the length cap, what counts as the owner's decision, the retry limits) and the mechanics (folders, ledger, exit codes, markers, the workers). The worker briefs are `briefs/analyst.md` (with `briefs/plan.schema.json`) and `briefs/checker.md` (with `briefs/checker.schema.json`). Transcripts are client material: follow the owner's data-privacy policy where they have one, and never copy a transcript, a note or a name into anything but the Portal and the state folder.

## Steps

1. [script] List the work. Run `python3 ~/.claude/skills/meeting-scheduled-worker/scripts/meeting_pending.py --limit N` (N from the request, else `rules.md`) and save its output as `RUN/pending.json`. For one named recording, run it with a limit large enough to include it and keep only that one; when it is not listed, say why from the output (acknowledged, unmatched, parked, waiting) and stop. A recording whose admin task the owner answered since the last run is listed again here like any other. → `ok`: step 2 → `nothing`: done → `not_local_owner`: stop → the command could not run: stop
2. [judgment] Take the next recording from `pending.json`'s `recordings`, in order, that this run has not handled. Before taking it, when the previous recording was skipped for a reason no command recorded (the analyst blocked, the check failed twice, a command could not run, a publish refusal), record it: `python3 ~/.claude/skills/meeting-scheduled-worker/scripts/meeting_skip.py RID --digest D --reason "<one line>"`. A command that exited 2 because the Portal was unreachable has already deferred the recording itself without counting an attempt; record nothing more for it. Keep a running list of each recording's outcome for the report. → no recording left: step 10 → a recording: step 3
3. [script] `REC` is `<state>/recordings/<RID>-<D>/`; run `python3 ~/.claude/skills/meeting-scheduled-worker/scripts/meeting_existing.py RID --digest D --out REC/existing.json`, which creates the folder and prints it as `folder`. `new` and `resume` go on to fetch; `published` means an earlier attempt wrote everything and only the acknowledgment is left. When the owner answered on the admin task (`answered` true), the command has already written the owner's words to `REC/answers.md` and set any earlier `plan.json` and `check.json` aside as `plan-N.json` and `check-N.json` (`set_aside`), so this recording is analysed again with the answers. → `new` or `resume`: step 4 → `published`: step 9 → `acknowledged`, `changed`, `unmatched`, `waiting` or `cancelled`: step 2 → the command could not run, or any result not named here: step 2
4. [script] Run `python3 ~/.claude/skills/meeting-scheduled-worker/scripts/meeting_fetch.py RID --digest D`. It writes `REC/source.json` and `REC/transcript.txt`, and `earlier_check` says whether `REC/plan.json` and a PASS `REC/check.json` from an earlier attempt still hold for this exact source: the same plan, checked against the same meeting note, with no answers the plan was not made with. Only then is the analysis skipped. Never skip it on your own reading of the folder: a note a human edited, or answers from the owner, make `earlier_check` false. → `ok` with `earlier_check` true: step 8 → `ok`: step 5 → `over_cap`, `no_transcript`, `no_note`, `changed` or `mismatch`: step 2 → the command could not run, or any result not named here: step 2
5. [hand-off: meeting-analyst] Dispatch the analyst with `briefs/analyst.md` and the paths of `REC/transcript.txt`, `REC/source.json` and `REC/existing.json`, plus `REC/answers.md` when it exists. On a revision round, add the errors from `meeting-validate` or the checker's numbered fixes and the path of the previous `REC/plan.json`. It returns the plan as one JSON block; save it verbatim as `REC/plan.json`, first moving an earlier round's plan to the next free `plan-N.json`. → BLOCKED: step 2 → a plan: step 6
6. [script] Run `python3 ~/.claude/skills/meeting-scheduled-worker/scripts/meeting_validate.py REC`. It checks every quote against the segment it names, the ids, the dispositions, and the tasks an earlier attempt made, and prints `plan_hash`, which covers the plan and the meeting note it was made against. → `invalid`: step 5 (max 2) → `invalid` after the last round: step 2 → `valid`: step 7
7. [hand-off: meeting-checker] Dispatch the checker with `briefs/checker.md`, the `plan_hash` from step 6, and the paths of `REC/transcript.txt`, `REC/source.json`, `REC/plan.json` and `REC/answers.md` when there is one. Never pass the analyst's prose or reasoning: the check is worth something only if the checker has not seen it. It returns PASS, or FAIL with numbered fixes, as one JSON block; save it verbatim as `REC/check.json`, first moving an earlier round's check to the next free `check-N.json`. → FAIL: step 5 (max 2) → FAIL after the last round: step 2 → PASS: step 8
8. [script] Run `python3 ~/.claude/skills/meeting-scheduled-worker/scripts/meeting_publish.py REC`. It reads `REC/answers.md` when it exists, refuses without a PASS check for this exact plan and note, finds each task by its marker before creating it, writes the note in place, verifies every write, sets the admin task DONE (or WAITING, with the plan's questions at the end of its description, when the plan has questions for the owner) and only then acknowledges the recording. A `waiting` result is recorded in the ledger, so later runs list the recording as waiting until the owner answers; collect its `questions` and `admin_task_id` for step 10. A `NOTE_EDITED` refusal with `permanent` true is one no retry cures: the command has marked the revision permanent, and the report lists it under needing the owner with the refusal's reason word for word. `BUSY` means another publish held this recording's folder; it is tried on a later run. → `published` or `waiting`: step 2 → `published_unacknowledged`: step 2 → refused `NOT_LOCAL_OWNER`: stop → refused `INVALID_PLAN`, `UNCHECKED`, `CHECK_FAILED`, `CHANGED_SINCE_CHECK` or `ANSWERS_UNAPPLIED`: step 2 → refused `TRANSCRIPT_CHANGED`, `LINKS_CHANGED`, `CANCELLED`, `WAITING` or `NOTE_EDITED`: step 2 → refused `MARKER_CONFLICT`, `MISSING_RECORD`, `READBACK_MISMATCH` or `LINK_NOT_VERIFIED`: step 2 → refused `BUSY`: step 2 → refused `DRY_RUN` (a dry run, nothing written): step 2 → the command could not run, or any result not named here: step 2
9. [script] Run `python3 ~/.claude/skills/meeting-scheduled-worker/scripts/meeting_acknowledge.py RID --digest D` for a recording whose note and tasks an earlier attempt already wrote. → `acknowledged` or `already_acknowledged`: step 2 → refused `NO_TASK`, `NOT_DONE`, `CHANGED`, `NO_NOTE`, `LINK_NOT_VERIFIED` or `ACK_NOT_VERIFIED`: step 2 → the command could not run, or any result not named here: step 2
10. [judgment] Write `RUN/report.md`: each recording handled, with its meeting title and date in the owner's timezone, the note link, the tasks created, reused and linked, and the flags (poor audio, uncertain speakers, duplicate admin tasks, enrichment skipped); each one skipped, with its reason, and those marked permanent (a note edit no retry cures) apart, with what the owner does to release them; each one waiting on the owner, with its admin task and its questions word for word, and how the owner answers (a comment on that task, or moving it to TODO); and from `pending.json`, how many remain and how many are waiting, parked, unmatched or over the cap. Then finish with the block under "Finishing". → the report written: done

**A skip is not a stop.** Every branch back to step 2 is that recording's outcome, not the run's. Before you act on a branch, read the evidence the command gave; when it contradicts what the branch assumes, record the recording as skipped with the command's reason and the evidence, verbatim, and move on. A result no branch names is treated the same way: recorded, skipped, reported, never guessed at. The ledger (`rules.md`) retries a skipped recording on a later run and parks it after three attempts, so nothing one recording does can hold the queue.

**A question is not a stop either.** A run never ends waiting for the owner. A recording with questions is written with everything they do not block, its admin task is WAITING with the questions in its description, and the run moves on. The owner answers in the Portal, by commenting on that admin task, by moving it to TODO, or both (a runner's own answer screen may post the answer on the task as a comment). A later run's `meeting-pending` lists the recording again, `meeting-existing` files the owner's comments (and the description, when they moved the task) as `REC/answers.md`, and the recording is analysed again with them. Until then the run report and the finishing block list it as waiting.

**Dry run.** When the request asks for a dry run (a runner says `Dry run: True`), pass `--dry-run` to `meeting-existing`, `meeting-fetch`, `meeting-publish` and `meeting-acknowledge`, and give every command that takes it (`meeting-pending`, `meeting-existing`, `meeting-fetch`, `meeting-publish`, `meeting-acknowledge`, `meeting-skip`) `--state` pointing at one scratch folder outside the toolbox repository, so `REC` and the ledger `meeting-skip` writes are the scratch copies. Everything is read and checked; nothing is written to the Portal and the real ledger is untouched. `python3 ~/.claude/skills/meeting-scheduled-worker/scripts/meeting_publish.py --dry-run` lists the writes it would make and leaves `REC/note-preview.md`. A runner that sets `F3I_TOOLBOX_DRY_RUN=1` makes every write command refuse a call that lacks `--dry-run`, so a forgotten flag writes nothing.

## Finishing

The last message of a run is one fenced JSON block:

```json
{"status": "done",
 "processed": [{"recording_id": "...", "title": "...", "note_id": "...", "tasks_created": 2,
                "tasks_reused": 0, "tasks_linked": 1, "acknowledged": true}],
 "waiting": [{"recording_id": "...", "title": "...", "admin_task_id": "...",
              "questions": ["Who owns sending the revised forecast?"]}],
 "skipped": [{"recording_id": "...", "title": "...", "reason": "the checker failed twice: ..."}],
 "remaining": 55,
 "flags": ["1090028b: two speakers share one label; attribution noted in the note"],
 "report": "RUN/report.md"}
```

or, when the run ended early:

```json
{"status": "stopped", "reason": "The Portal hands Fellow processing to the cloud; nothing was written.",
 "processed": [], "waiting": [], "skipped": [], "remaining": 60, "flags": [], "report": "RUN/report.md"}
```

`remaining` is `pending.json`'s `remaining_after_this_run`. `title` is the meeting's title as the Portal holds it. `waiting` lists the recordings this run left WAITING on the owner, each with its admin task and its questions; never end with a `needs_owner` block.

## When no one is present

The steps are the same, and nothing waits on a person: questions go to the admin task, the report and the finishing block, never to the session. Nothing that is the owner's decision is guessed.

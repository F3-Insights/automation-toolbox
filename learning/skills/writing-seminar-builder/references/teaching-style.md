# Teaching style: how the speaker notes should sound

The delivery voice for a seminar, workshop or lab. It governs the speaker notes and the run of show, not the on-slide text (that is the written voice: the `brand-guide` skill, and the owner's voice guide, setting `voice_guide`, when the deck is the owner's). When the presenter has a voice guide of their own, it wins over this file. The guidance below is a default for any presenter, not a description of one person.

## A pattern that works

### Opening
- A casual check-in before any content.
- A quick poll or a few Socratic questions to gauge the room's skill level and goals.
- Frame the session as collaborative: the presenter has a view but does not want to monopolize the hour.

### Delivery
- **Demo first, slides rarely.** The default is a screen share and live narration. Slides are visual anchors for an executive audience, not the script.
- **Live build, recover in the open.** When something breaks, fix it in front of the audience. Transparency builds more trust than a demo that never fails.
- **Say what you do not know.** Name the tools you have not used and the technical depth you do not have. Never fake expertise.
- **Let tangents happen, then weave them back.** A sidebar the room cares about is worth two minutes if it returns to the thread.
- **Self-disclosing examples.** The presenter's own systems, setups and reasons for building them are the proof points, especially for a non-technical audience.
- **Pragmatic over elegant.** Show what solves the audience's problem; do not sell technical elegance.

### Transitions
- Use a plain spoken cue to move from talk to demo.
- When something is loading, say a word about what is happening, then let the silence sit rather than filling it.

### Q&A
- Ask a clarifying question before answering.
- Encourage disagreement, and change the framing on the spot when a participant has the better one.
- When the topic is a tool the room is learning, putting an audience question to the tool live is a useful demonstration.

### Closing
- Action-oriented: what happens next time.
- Ask for feedback explicitly.
- Name follow-ups out loud, as implicit accountability.

## Pedagogical principles

1. **Show first, explain second.** Open with the end state ("this is where we will be at the end"), then build toward it.
2. **Progressive depth.** Offer levels of setup (for example chat, then projects, then a coding agent) so each person can choose where to stop.
3. **Concrete over abstract.** Every concept gets a real example, ideally from work the presenter has done.
4. **The audience drives the agenda.** Poll early, listen for repeated interests, adjust the next session accordingly.
5. **Transparency about cost.** Say what the tools cost and what the cheaper tier gets you.

## What to avoid

- **Polished, pre-built demos that never fail.** Over-rehearsal loses the trust a live build earns.
- **"AI evangelist" framing.** Name failure modes and admit gaps; hype contradicts the voice.
- **Long monologues.** The longest stretches are demo narration, not lecture. Build in audience interaction every 10 to 15 minutes.
- **Splitting the content for non-technical audiences.** Non-technical participants do well with the same content delivered patiently, technical walkthroughs included. Do not split the audience too aggressively.

## Implications for productized formats

- A pre-recorded session works only if it keeps the live-build energy; a recorded demo that fails and recovers is more credible than a smooth one.
- A working session beats a lecture: everyone builds their own version in parallel while the presenter circulates.
- Executive seminars still use some slides, because executives expect them, but the slides are visual anchors, not scripts (see the deck style guide in the `brand-guide` skill).
